HTTP-сервис 1С для интеграций: как сделать безопасно

Когда к 1С подключают сайт, Telegram-бота, CRM и ещё пару сервисов, учётная база по сути получает выход в интернет. От того, как он устроен, зависит сохранность клиентской базы, заказов и денег. Разберём, как работает собственное API 1С, где обычно возникают риски и как владельцу проверить интеграцию без знаний программирования.

Коротко

Как устроен HTTP-сервис и собственное API 1С для ботов, CRM и сайта: публикация, доступы, права, защита от дублей и журнал обмена. Чек-лист для владельца.

01Зачем 1С собственное API, а не ещё одна выгрузка

Знакомая картина в выросшем магазине: сайт обменивается с 1С файлами по расписанию, бот берёт данные из отдельной таблицы, CRM синхронизируется через сторонний сервис. У каждого соединения свои правила, свои ошибки и своё место, где теряются данные. Если заказ не дошёл, непонятно, на каком шаге он пропал.

HTTP-сервис — механизм платформы 1С, который позволяет принимать и отдавать данные через интернет-запросы, как это делают обычные веб-сервисы. Собственное API — набор чётко описанных «дверей»: создать заказ, получить статус, найти клиента. Сайт, бот и CRM входят через одни и те же двери по общим правилам, поэтому новая интеграция не требует отдельного костыля.

02Откуда риск: учёт становится доступен снаружи

Чтобы сервис получил данные, одна сторона должна достучаться до другой. Проще всего опубликовать базу на веб-сервере и открыть её в интернет. Частые ошибки: публикуют базу целиком вместе с веб-клиентом, включают стандартный интерфейс OData и открывают через него все объекты «на всякий случай», подключаются под администратором, работают без HTTPS.

Другой вариант — промежуточная серверная часть. Внешние сервисы общаются с ней, а 1С обменивается только с ней, так что публичный адрес не ведёт напрямую в учётную базу. Какую схему выбрать, зависит от того, где стоит 1С, есть ли постоянный адрес сервера и кто его обслуживает.

03Кто вправе обращаться: доступы и права

Для обмена нужен отдельный пользователь 1С с правами только на нужные операции — не администратор и не учётная запись менеджера. Если данные для входа утекут, ущерб ограничится тем, что разрешено этому пользователю.

У каждого потребителя API должен быть свой ключ: у бота, у CRM, у сайта. Тогда один ключ можно отозвать, не останавливая остальные, а в журнале видно, кто именно делал запрос. Ключи не пересылают в мессенджерах и не оставляют в коде, выложенном в открытый доступ.

HTTPS обязателен — без него логины и данные клиентов передаются открытым текстом. Если запросы приходят с постоянного IP-адреса, доступ стоит ограничить только им.

04Что отдавать и что принимать

Принцип минимума: боту, который показывает клиенту статус заказа, незачем видеть весь список клиентов или историю оплат. Каждый метод возвращает ровно те поля, которые нужны для задачи. Поиск заказа по номеру лучше совмещать с проверкой телефона, чтобы чужой заказ нельзя было открыть перебором номеров.

Входящие данные проверяются: формат телефона, наличие товара в справочнике, допустимые статусы. Цены и суммы от внешней стороны не стоит принимать на веру — надёжнее сверять их с ценами в учёте.

Отдельная ловушка — повторные запросы. Связь оборвалась, сервис не дождался ответа и отправляет тот же заказ ещё раз. Если API этого не учитывает, в учёте появляются дубли. Обычное решение — уникальный номер заказа сайта или запроса, по которому 1С понимает, что такой документ уже есть.

05Журнал обмена: без него безопасности нет

Даже хорошо настроенный обмен когда-нибудь даст сбой. Журнал фиксирует, что пришло, откуда, когда и чем закончилось. Он нужен и для разбора жалобы «заказ не дошёл», и чтобы вовремя заметить странное: запросы посреди ночи, серию ошибок входа, обращения из неизвестного источника.

Важно, чтобы журнал был доступен менеджеру или владельцу прямо в 1С, а не только в логах сервера, куда заглядывает лишь программист.

07Как проверить, что интеграция безопасна: чек-лист

Спросите у исполнителя, под каким пользователем работает обмен и какие у него права. Ответ «под администратором» — повод всё переделать. Попросите показать, какие методы доступны снаружи и что возвращает каждый.

Проверьте на практике: запрос без ключа или с неверным ключом должен получить отказ, а в журнале должна появиться запись. Отправьте один и тот же тестовый заказ дважды — дубля быть не должно. Смените статус в 1С и посмотрите, обновился ли он на сайте. Отзовите ключ бота и убедитесь, что сайт и CRM продолжают работать.

После смены сотрудников или подрядчика замените ключи доступа — так бывший исполнитель теряет доступ к вашей базе.

Частые вопросы

безопасно ли публиковать базу 1С в интернет

Опасна не сама публикация, а то, что именно открыто и с какими правами. Безопасная схема — только нужные методы, отдельный пользователь с минимальными правами, HTTPS и журнал запросов.

чем HTTP-сервис отличается от OData в 1С

OData — стандартный интерфейс, через который можно открыть справочники, документы и регистры базы целиком. HTTP-сервис — собственные методы под конкретные задачи с вашими проверками, поэтому для ботов и CRM его проще контролировать.

как подключить Telegram-бота к 1С без доступа ко всей базе

Бот получает отдельный ключ и доступ только к нужным методам, например к статусу заказа по номеру и телефону. Остальные данные для него закрыты.

нужно ли менять конфигурацию 1С для API

Нет, хаб обмена устанавливается расширением без изменения конфигурации. Сначала его ставят на копию базы и проверяют там.

как быстро заказ с сайта появляется в 1С через API

Сразу после оформления, без ожидания расписания. Ход обмена виден в журнале.
