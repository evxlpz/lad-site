HTTP-сервіс 1С для інтеграцій: як влаштувати безпечно

Коли до 1С підключають сайт, Telegram-бота, CRM і ще кілька сервісів, облікова база фактично отримує вихід в інтернет. Від того, як його зроблено, залежить, чи будуть у безпеці клієнтська база, замовлення й гроші. Розберемо, як влаштоване власне API 1С, де найчастіше виникають ризики і як власникові перевірити інтеграцію, не будучи програмістом.

Коротко

Як працює HTTP-сервіс і власне API 1С для ботів, CRM і сайту: публікація, доступи, права, захист від дублів і журнал обміну. Чекліст перевірки для власника.

01Навіщо 1С власне API, а не ще одне вивантаження

Типова картина в магазині, що виріс: сайт обмінюється з 1С файлами за розкладом, бот бере дані з окремої таблиці, CRM синхронізується через сторонній сервіс. Кожне з’єднання має свої правила, свої помилки й своє місце, де губляться дані. Коли замовлення не дійшло, незрозуміло, на якому кроці воно зникло.

HTTP-сервіс — це механізм платформи 1С, що дає змогу приймати й віддавати дані через інтернет-запити, як це роблять звичайні вебсервіси. Власне API — набір чітко описаних «дверей»: створити замовлення, отримати статус, знайти клієнта. Сайт, бот і CRM заходять через ті самі двері за однаковими правилами, тож нова інтеграція не потребує окремого костиля.

02Звідки береться ризик: облік стає доступним ззовні

Щоб сервіс отримав дані, одна сторона має достукатися до іншої. Найпростіший шлях — опублікувати базу на вебсервері й відкрити її в інтернет. Типові пастки: публікують базу цілком разом із вебклієнтом, вмикають стандартний інтерфейс OData і відкривають через нього всі об’єкти «про всяк випадок», підключаються під обліковим записом адміністратора, працюють без HTTPS.

Інший підхід — проміжна серверна частина. Зовнішні сервіси спілкуються з нею, а 1С обмінюється лише з нею. Тоді публічна адреса не веде напряму в облікову базу. Яку схему обрати, залежить від того, де стоїть 1С, чи є постійна адреса сервера і хто його адмініструє.

03Хто має право звертатися: доступи й права

Для обміну потрібен окремий користувач 1С із правами лише на потрібні операції — не адміністратор і не обліковий запис менеджера. Якщо дані для входу потраплять не в ті руки, шкода обмежиться тим, що дозволено цьому користувачеві.

Кожен споживач API повинен мати власний ключ: окремий для бота, окремий для CRM, окремий для сайту. Так можна відкликати один ключ, не зупиняючи решту, а в журналі видно, хто саме робив запит. Ключі не пересилають у месенджерах і не залишають у коді, викладеному у відкритий доступ.

HTTPS обов’язковий — без нього логіни й дані клієнтів передаються відкритим текстом. Якщо запити надходять із постійної IP-адреси, доступ варто обмежити лише нею.

04Що віддавати і що приймати

Принцип мінімуму: бот, який показує клієнтові статус замовлення, не повинен мати змоги отримати весь список клієнтів чи історію оплат. Кожен метод повертає рівно ті поля, які потрібні для задачі. Пошук замовлення за номером краще поєднувати з перевіркою телефону, щоб чуже замовлення не можна було переглянути, перебираючи номери.

Вхідні дані перевіряються: формат телефону, наявність товару в довіднику, допустимі статуси. Ціни й суми не варто брати на віру від зовнішньої сторони — надійніше звіряти їх із цінами в обліку.

Окрема пастка — повторні запити. Зв’язок обривається, сервіс не дочекався відповіді й надсилає те саме замовлення ще раз. Якщо API цього не враховує, в обліку з’являються дублі. Звичне рішення — унікальний номер замовлення сайту або запиту, за яким 1С розпізнає, що такий документ уже існує.

05Журнал обміну: без нього безпеки немає

Навіть добре налаштований обмін колись дасть збій. Журнал фіксує, що прийшло, звідки, коли і чим закінчилося. Він потрібен, щоб розібрати скаргу «замовлення не дійшло» і вчасно помітити незвичне: запити серед ночі, серію помилок входу, звернення з невідомого джерела.

Важливо, щоб журнал був доступний менеджерові чи власникові в самій 1С, а не лише в логах сервера, куди заглядає тільки програміст.

06Як це влаштовано в хабі обміну

Хаб обміну — модуль для 1С:УНФ і BAS Малий бізнес, що зв’язує сайт з обліком. Замовлення передається в 1С одразу після оформлення, без очікування розкладу. Менеджер працює з ним в обліку, як звик, а зміна статусу в 1С повертається на сайт і клієнтові. Клієнти й історія замовлень синхронізовані.

Модуль має власне API для ботів, CRM та інших сервісів, тож нову інтеграцію підключають без окремого костиля. Журнал обміну показує, що і коли пройшло. Для роботи потрібні доступ до сайту, щоб встановити серверну частину, і 1С з доступом до інтернету. Для Bitrix обмін готовий; під Laravel, Хорошоп, Prom, Rozetka, OpenCart, WooCommerce, Odoo, Zoho та інші системи серверна частина адаптується через їхнє API після оцінки. Типовий обмін для каталогу часто лишають, а замовлення й статуси переводять на хаб.

Які методи відкривати і для кого, визначається під вашу задачу на етапі розбору; потрібні обмеження доступу налаштовуються після оцінки. Модуль ставиться як розширення без зміни конфігурації, спершу на копію бази. Дані лишаються у вашій базі, оплата разова без абонплати, а протягом 30 днів після запуску помилки виправляються.

07Як перевірити, що інтеграція безпечна: чекліст

Запитайте виконавця, під яким користувачем працює обмін і які в нього права. Якщо відповідь «під адміністратором» — це привід усе переробити. Попросіть показати, які саме методи доступні ззовні й що повертає кожен.

Перевірте поведінку на практиці: запит без ключа або з неправильним ключем має отримати відмову, а в журналі має з’явитися запис. Надішліть те саме тестове замовлення двічі — дубля бути не повинно. Змініть статус у 1С і подивіться, чи оновився він на сайті. Відкличте ключ бота й переконайтеся, що сайт і CRM працюють далі.

Після зміни працівників або підрядника замініть ключі доступу — так колишній виконавець утрачає доступ до вашої бази.

Часті питання

чи безпечно публікувати базу 1С в інтернет

Небезпечна не сама публікація, а те, що саме відкрито і з якими правами. Безпечна схема — лише потрібні методи, окремий користувач з мінімальними правами, HTTPS і журнал запитів.

чим HTTP-сервіс відрізняється від OData в 1С

OData — стандартний інтерфейс, через який можна відкрити довідники, документи й регістри бази цілком. HTTP-сервіс — це власні методи під конкретні задачі з вашими перевірками, тому для ботів і CRM його легше контролювати.

як підключити Telegram-бота до 1С без доступу до всієї бази

Бот отримує окремий ключ і доступ лише до потрібних методів, наприклад статусу замовлення за номером і телефоном. Решта даних для нього закрита.

чи треба змінювати конфігурацію 1С для API

Ні, хаб обміну встановлюється як розширення без зміни конфігурації. Спершу його ставлять на копію бази й перевіряють там.

як швидко замовлення з сайту з’являється в 1С через API

Одразу після оформлення, без очікування розкладу. Хід обміну видно в журналі.
