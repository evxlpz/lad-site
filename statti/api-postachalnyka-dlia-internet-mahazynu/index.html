API постачальника: залишки, ціни й статуси в 1С

Коли постачальник має API, частину щоденної рутини можна передати обліку: дзвінки «чи є в наявності», листи з прайсами, звіряння підтверджень. Проте API в різних постачальників дуже різні: один віддає лише «є/нема», інший показує залишки по складах, ціни й статус кожного замовлення. Розбираємо, які дані зазвичай доступні, де типові пастки і що з’ясувати до початку інтеграції.

Коротко

Які дані можна автоматично брати з API постачальника в 1С: залишки, ціни, підтвердження й статуси замовлень, що спитати в постачальника і як перевірити обмін.

01API постачальника: що це і чим воно краще за прайс на пошту

API — це машинний канал. Через нього ваша 1С сама запитує в системі постачальника потрібні дані й отримує відповідь у структурованому вигляді. Людині не треба відкривати лист і переносити цифри: програма робить запит і розкладає відповідь по полях. Прайс в Excel показує стан на момент вивантаження, а відповідь API — на момент запиту.

Для магазину це означає менше ручного перенесення й менше помилок у цифрах. Але API — лише двері, а що за ними, вирішує постачальник. Тому перш ніж планувати автоматизацію, варто переглянути його документацію: які дані він віддає, у якому вигляді і чи можна через API не лише читати, а й надсилати замовлення.

02Залишки: кількість, «є/нема» і склади

Залишки постачальники дають найчастіше. Форматів кілька: точна кількість, градації на кшталт «багато / мало / немає» або проста ознака наявності. Дехто показує залишки окремо по кожному своєму складу, інколи разом з очікуваною датою надходження.

Типова пастка — вважати залишок постачальника гарантованим. Між вашим запитом і його відвантаженням товар може купити інший клієнт, а частина складу може бути вже зарезервована. Тому варто уточнити, що саме показує API — вільний залишок чи загальний, і закласти запас: наприклад, не вважати товар доступним, коли в постачальника лишилися одиничні штуки.

Друга пастка — склади. Якщо постачальник відвантажує з різних міст, строк доставки до вас буде різним. Які склади враховувати, а які ні, краще вирішити до запуску, а не після першого замовлення, що «застрягло» на далекому складі.

03Ціни: закупівельні, рекомендовані, валюта

Через API постачальник може віддавати вашу закупівельну ціну, рекомендовану роздрібну, акційні ціни. Важливо з’ясувати, чи враховує відповідь ваші персональні умови: часто API показує базову ціну, а знижка з’являється вже в рахунку.

Не менш важливі валюта, ПДВ і одиниця виміру. Ціна може бути в іноземній валюті, з ПДВ або без нього, за штуку чи за упаковку. Якщо не врахувати цього під час налаштування, у 1С з’являться ціни, які формально «прийшли автоматично», але не відповідають рахунку. На перших оновленнях звіряйте кілька позицій вручну.

Окреме рішення — що робити, коли ціна змінилася: тихо оновити закупівельну чи показати зміну менеджерові, щоб він переглянув роздрібну. Автоматика пришвидшує роботу, але відповідальності за націнку не знімає.

04Замовлення і статуси: підтвердження, часткове виконання, відвантаження

Друга половина обміну працює у зворотний бік: ваше замовлення йде постачальнику, а він відповідає. Найкорисніше, що може повернути API, — підтвердження: що прийнято, в якій кількості, за якою ціною. Далі можуть надходити статуси — зібрано, відвантажено, скасовано, а в деяких постачальників ще й номер відправлення чи документа.

Часткове підтвердження — головна причина, чому прихідні накладні не сходяться із замовленням. Ви замовили кілька позицій, постачальник підтвердив не всі, і ця різниця загубилася в листуванні. Якщо відповідь потрапляє в облік, розбіжність видно одразу, ще до того, як товар пообіцяли покупцеві.

Статуси постачальника рідко збігаються з вашими. Під час налаштування їх треба зіставити: які його стани означають «прийнято», які — «відмова», і що робити з новим, невідомим статусом, щоб він не зник непомітно.

05Що спитати в постачальника до початку інтеграції

Кілька питань, які заощаджують час: чи є документація і тестовий доступ; як видається ключ доступу і чи можна мати окремий ключ саме для 1С; чи є обмеження на кількість запитів; за яким ідентифікатором шукати товар — артикул, штрихкод чи внутрішній код постачальника; чи приймає API замовлення, чи дає лише читати дані.

Також варто дізнатися, хто з боку постачальника відповідає за API і чи попереджають там про зміни. Якщо формат відповіді змінять без попередження, обмін зупиниться, і краще заздалегідь знати, до кого звертатися.

Окреме питання — відповідність товарів. Ваша номенклатура і каталог постачальника майже ніколи не збігаються один в один: інші назви, артикули з префіксами, інші одиниці. Без зіставлення залишки й ціни просто немає до чого прив’язати.

06Як перевірити, що обмін справді працює

У перші дні після запуску порівнюйте дані в 1С з кабінетом постачальника на кількох товарах: залишок, ціну, статус свіжого замовлення. Зробіть пробне замовлення і простежте, чи повернулося підтвердження і чи збігаються кількості.

Далі — помилки. API буває недоступним, ключ втрачає чинність, товар зникає з каталогу. Важливо, щоб кожна невдала спроба лишала слід, який видно без програміста: що відправлено, що повернулося, на чому зупинилося. Інакше обмін «працює», доки хтось не помітить, що залишки давно не оновлювалися.

І ще одне: вирішіть, що показує облік, коли зв’язку з постачальником немає, — останні відомі дані чи нуль. Це рішення краще ухвалити свідомо, ніж дізнатися про нього від покупця.

07Як це вирішує модуль «Обмін з постачальником»

Залишки постачальника видно в обліку, статуси й відповіді приходять назад, а помилки обміну видно в журналі, тож нічого не губиться мовчки.

У кожного постачальника свій API, тому модуль адаптується під конкретного. Підключити можна скільки завгодно постачальників, кожен новий — окрема адаптація. Відповідність ваших товарів товарам постачальника налаштовуємо разом. Ціни через API, номери відправлень та інші поля, якщо постачальник їх віддає, доробляються після оцінки його документації. Якщо API немає, можна працювати з файлами Excel, CSV чи XML — спершу оцінюємо, чи варто.
